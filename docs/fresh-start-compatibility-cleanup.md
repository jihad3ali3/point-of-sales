# خطة إعادة البناء النظيف وإزالة توافق التثبيتات القديمة

> **الحالة:** خطة للمراجعة والتنفيذ اللاحق؛ لم يُنفّذ أي حذف أو تعديل على قاعدة البيانات ضمن هذا المستند.
>
> **المرجع:** commit `69b93642dc4d0f5596db8fecb4e5c5d892ec5b38` على `main`.
>
> **التاريخ:** 2026-10-30.
>
> **الافتراض المقبول:** البيانات التشغيلية الحالية تجريبية ويمكن فقدانها. المطلوب هو نظام يعمل بالوظائف الحالية نفسها، لكن بمخطط ومسارات داخلية لا تحمل قواعد ترقية التثبيتات القديمة.

## 1. القرار والهدف

هذه ليست عملية حذف migrations قديمة فقط. كثير من مسارات التوافق ما زال يكتب ويقرأ أثناء التشغيل. حذف العمود أو الـfallback أولًا قد يعطّل البيع، المخزون، الاستيراد، الدفع، التقارير أو الواجهة العامة للعميل.

النتيجة المطلوبة هي:

1. مخطط قاعدة بيانات نهائي يُنشأ مباشرة بالشكل الصحيح على قاعدة فارغة.
2. لا توجد backfills لبيانات قديمة، ولا فحوص من نوع «أضف العمود إذا لم يكن موجودًا»، ولا مسارات تقرأ سجلات تشغيلية غير معروفة المالك.
3. لا توجد كتابتان متزامنتان للقيمة نفسها مثل `products.stock` و`product_warehouse.stock`، أو بيانات الدفع المكررة بين المعاملة والـtenders.
4. تبقى عقود HTTP وواجهات المستخدم والتقارير والطباعة والوظائف الحالية كما هي، حتى لو تغيّر مصدر القيمة داخليًا.
5. تكون عملية الانتقال **one-way destructive reset** موثقة، وليست ترقية تحافظ على البيانات القديمة.

### خارج النطاق

- إعادة تصميم واجهات المستخدم أو إضافة ميزات جديدة.
- تغيير طريقة احتساب الأرباح أو تقارير الوردية أو قواعد التسعير.
- حذف كل عمود nullable أو كل fallback؛ بعضها سلوك مقصود حالي.
- حذف الحماية من seed البيانات التجريبية في production، أو حماية الصلاحيات، أو عزل المستودعات.
- دعم ترقية قاعدة قديمة إلى المخطط الجديد بعد هذه النسخة.

## 2. أساس التحليل وقاعدة التصنيف

اعتمد الجرد على الشيفرة والـmigrations والـseeders والاختبارات والتوثيق الموجودة في المرجع أعلاه، وعلى تاريخ المشروع الأصلي الذي جاء منه الـfork. لا يعتمد هذا المستند على مستندات أو تعديلات أنشأها مساعد سابقًا.

قبل حذف أي جزء، يُصنَّف ضمن واحد من الآتي:

| التصنيف | القرار |
|---|---|
| كتابة/قراءة توافق لبيانات ما قبل multi-warehouse أو multi-outlet أو split tender | تُنقل الوظيفة إلى المصدر canonical أولًا، ثم يُحذف مسار التوافق |
| تعديل مخطط أو backfill لا معنى له على قاعدة فارغة | يُدمج الشكل النهائي في migrations الإنشاء، ويُحذف الـbackfill |
| قيمة NULL تعني إعدادًا عامًا أو fallback موثقًا | تبقى NULL ويبقى الـfallback |
| قيمة NULL لحالة مشروعة مثل مسودة مرتجع | تبقى، مع فرض القيود المناسبة عند اكتمال الحالة |
| وظيفة نشر أو حماية أو idempotency في seeder | تبقى؛ ليست توافقًا قديمًا لمجرد أنها تفحص حالة أو تكرر التنفيذ بأمان |
| حقل غير مستخدم لكنه لا يمثل توافقًا مؤكدًا | لا يُحذف تلقائيًا؛ يحتاج قرار منتج مستقل |

## 3. الحالة النهائية المطلوبة

بعد التنفيذ يجب أن تكون الحقائق التالية صحيحة:

- `product_warehouse` هو مصدر رصيد المخزون القابل للتعديل، وكل رصيد له `warehouse_id` معروف.
- الوحدة الأساسية لكل منتج غير مركب صريحة في `product_units`، والكميات المخزنية بوحدة الأساس.
- `transaction_detail_batch_allocations` هو سجل توزيع الكميات على الـbatches؛ لا يوجد مؤشر «أول batch» بديل عنه.
- لكل عملية بيع فعلية `warehouse_id` و`cashier_shift_id`، ولكل سلة `warehouse_id` يطابق الوردية النشطة.
- الدفع المفرد والدفع المقسّم يُمثلان داخليًا عبر `transaction_tenders`. المعاملة تحتفظ بالملخص اللازم للعقود الحالية، لا بمسار دفع ثانٍ مستقل.
- السجلات المالية والمخزنية التشغيلية لها مالك واضح. أما إعدادات النظام والدفع والتسعير العامة فيبقى `outlet_id = NULL` عندما تعني «عام».
- لا توجد أوامر مخصصة لإصلاح تثبيتات قديمة، ولا browser migration لصفوف offline القديمة مجهولة النطاق.
- `migrate:fresh --seed` على قاعدة فارغة ينتج النظام كاملًا، ثم تُستعاد بيانات المناطق المرجعية وتُضبط المنافذ والمستودعات والمستخدمون عبر المسارات الحالية.

## 4. جرد التغييرات

### 4.1 الـmigrations: بناء الشكل النهائي بدل إعادة تمثيل تاريخ الترقية

المخطط الحالي يتكون من إنشاء الجداول ثم سلسلة طويلة من `add column` و`change()` وإدخال بيانات داخل migrations. بعض العمليات موجودة فقط لتفادي اختلاف التثبيتات السابقة، ومنها:

- إضافة `avatar` مرتين، مع `Schema::hasColumn` في:
  - `2024_06_13_091315_add_avatar_field_to_users_table.php`
  - `2025_12_30_000000_add_user_avatar_column_if_missing.php`
- فحوص `Schema::hasTable/hasColumn` في migrations نطاق المنافذ.
- إنشاء `PUSAT` وربط المستخدمين والمستودعات القديمة به داخل migrations.
- نسخ المخزون والوحدات والـwarehouse IDs إلى جداول جديدة.
- تحويل أسرار الدفع النصية إلى القيم المشفرة.
- تعبئة حقول التسعير من أسعار قديمة.
- إدخال defaults للوحدات والإعدادات والضرائب والولاء من داخل migrations.
- migrations لاحقة تجعل صور وأوصاف المنتجات والتصنيفات nullable.

#### التغيير المطلوب

1. إنشاء baseline مرتب حسب الاعتماديات، ويفضل أن يبقى مقسمًا إلى migrations منطقية بدل ملف عملاق واحد.
2. دمج كل `add column` وتعديل nullable والفهارس في migration إنشاء الجدول المعني.
3. إعادة ترتيب الإنشاء حيث يلزم؛ مثلًا يجب إنشاء `outlets` و`warehouses` و`cashier_shifts` قبل الجداول التي ستشير إليها بمفاتيح غير nullable.
4. الاحتفاظ بمفاتيح `client_uuid` و`sync_fingerprint` وفهارسها والقيود الحالية؛ هذه وظائف offline/idempotency حالية، وليست توافقًا.
5. الاحتفاظ بأعمدة الأسرار من نوع `text` وبالـencrypted casts في النماذج. يُحذف تحويل البيانات القديمة، لا التشفير.
6. نقل defaults والبيانات المرجعية إلى seeders حتمية وقابلة للتكرار بأمان.
7. عدم حذف migrations المناطق الأربع الخاصة بـ`laravolt/indonesia`؛ إنها تنشئ مخططًا مطلوبًا حاليًا.
8. الاحتفاظ بدوال `down()` المنطقية للمخطط الجديد، لكن لا حاجة إلى `down()` يعيد بناء تثبيت قديم ببياناته.

#### ما يُحذف بدل نقله

- كل backfill يعتمد على وجود سجلات قديمة.
- فحوص «الجدول/العمود موجود لأن بعض التثبيتات قد تكون نفذت جزءًا من الترقية».
- إسناد كل المستخدمين القدامى إلى `PUSAT`.
- نسخ `products.stock` إلى `product_warehouse`.
- إنشاء وحدات افتراضية من بيانات منتجات قديمة داخل migration.
- تشفير القيم القديمة بقراءتها وتعديلها داخل migration.
- تحديث `PUSAT.is_sales_enabled` في migration بيانات؛ تفرضه بذرة الإعداد الأولي مباشرة.

> **تحذير:** لا يجوز حذف الـmigrations القديمة مع إبقاء migrations لاحقة تعتمد على أعمدة كانت تنشئها. يجب استبدالها بمخطط نهائي متماسك ثم اختبار إنشائه من الصفر.

### 4.2 الـseeders والإعداد الأولي

يُعدّل `DatabaseSeeder` والـseeders المتخصصة بحيث تكون مسؤولة عن:

- إنشاء `PUSAT` كمنفذ مركزي غير بائع، وإنشاء المستودع المركزي و`setup_warehouse_id` كما يتطلب `SetupController`.
- إنشاء الوحدات الأساسية دون افتراض أن ID الوحدة يساوي `1`.
- إنشاء defaults للإعدادات العامة والضرائب والولاء وdine-in.
- إنشاء الأدوار والصلاحيات بأسمائها canonical مباشرة.
- إنشاء بيانات العرض، عند طلبها صراحة، عبر خدمات المخزون canonical بدل كتابة رصيدين متطابقين.

ما يُحذف:

- تطبيع صلاحيات أدوار قديمة مثل تحويل أسماء `permission-access` أثناء كل seed.
- نسخ `products.stock` إلى الـpivot.
- schema guards التي هدفها تشغيل demo seeder على مخطط قديم ناقص.

ما يبقى:

- `firstOrCreate`/`updateOrCreate` عندما يكون غرضه جعل الـseeder قابلًا للتكرار.
- منع demo seed/reset في production.
- استثناء جداول `indonesia_*` في `DemoDatabaseResetter`.
- إنشاء المنافذ البائعة والمستودعات وإسناد المستخدمين عبر setup وإدارة المستخدمين الحالية.

### 4.3 المخزون: إزالة `products.stock` دون إزالة حقل `stock` من العقود

`products.stock` ليس عمودًا ميتًا حاليًا. توجد كتابات وقراءات له في CRUD وAPI والاستيراد والتصدير والـresources وPOS والمرتجعات والمشتريات وopname والتقارير وdine-in والـseeders. لذلك الحذف المباشر ممنوع.

#### المصدر النهائي

- الرصيد القابل للتعديل هو `product_warehouse.stock`.
- `StockMutationService`، أو خدمة داخلية واضحة تحل محله، هي نقطة الكتابة الوحيدة للرصيد والـmutation.
- كل تغيير يقفل صف الـpivot المناسب، ويحوّل الكمية إلى وحدة الأساس، ويكتب `stock_before/stock_after` بالدلالة نفسها في جميع العمليات.
- لا تُنشأ mutation جانبية ثانية لتصحيح مجموع قديم.

#### تحويل القراءات

- يبقى مفتاح `stock` في `ProductResource` وAPI والتصدير، لكنه **مجموع محسوب** من المستودعات المناسبة.
- عند وجود وردية نشطة، يعرض POS رصيد مستودع الوردية فقط.
- عند السماح باستعراض منتجات Mobile API بلا وردية، يُحسب المجموع من المستودعات المسموح بها للمستخدم بدل قراءة `products.stock`.
- التقارير التي تحتاج مجموعًا عامًا تستخدم `SUM(product_warehouse.stock)`، والتقارير المقيدة بمنفذ تستخدم مستودعات ذلك المنفذ فقط.
- مرشحات «متوفر» و«منخفض المخزون» وقيم المخزون تُعاد كتابتها على الـpivot.

#### تحويل الكتابات

- إنشاء منتج برصيد ابتدائي يتطلب مستودع وجهة صريحًا.
- استيراد المنتجات يستخدم مستودعًا مختارًا بوضوح، أو عمود مستودع في القالب؛ لا يكتب رصيدًا عالميًا مجهول الموقع.
- تعديل الرصيد عبر API يتحول إلى delta mutation على مستودع محدد. تعديل بيانات المنتج دون إرسال رصيد لا يغيّر المخزون.
- المشتريات والاستلام والمرتجعات وopname والتحويلات والبيع وdine-in تستخدم الخدمة نفسها.
- المنتجات المركبة تبقى وفق منطق المكونات الحالي، ولا تُعامل كمنتج عادي له وحدة بيع أو رصيد مستقل إلا إذا كان ذلك هو السلوك الحالي الموثق.

بعد نجاح اختبارات التكافؤ يُحذف عمود `products.stock` وكل dual write وكل fallback إليه.

### 4.4 الوحدات والتسعير والـbatches

#### الوحدات

- لكل منتج غير مركب سجل وحدة أساس صريح في `product_units`.
- `unit_id = 1` ليس قيمة افتراضية. تُستخرج الوحدة من علاقة المنتج الفعلية.
- لا يُستخدم `conversion_factor = 1` أو سعر `products.sell_price` للتستر على وحدة مفقودة.
- `UnitConversionService::toBaseUnit` و`getSellPrice` يستخدمان وحدة صريحة، ويرفضان بخطأ واضح منتجًا غير مركب ناقص إعداد الوحدات.
- يبقى `unit_id = NULL` للمنتج المركب حيث يكون ذلك مقصودًا.
- تبقى `conversion_factor` والسعر والخصومات داخل cart/detail كـsnapshots تاريخية؛ لا يعاد احتسابها من إعدادات لاحقة.
- يمكن بقاء `products.sell_price` لاستخدامات الكتالوج أو السعر الافتراضي، لكن لا يكون fallback يخفي غياب وحدة البيع.

#### الـbatches

- `transaction_details.product_batch_id` مؤشر قديم لا يكفي لتمثيل البيع من أكثر من batch.
- كل بيع يستخدم `transaction_detail_batch_allocations`، بما في ذلك حالات FEFO والاسترجاع والإلغاء.
- تُحذف العلاقة والكتابات والقراءات الخاصة بالمؤشر القديم ثم يُحذف العمود.
- تبقى بيانات `product_batches` والتنبيهات والانتهاء والتحويلات؛ فهي وظائف حالية.
- الحقولان `stock_mutations.batch_number/expired_at` لا يمثلان مصدر الحقيقة ويُحذفان بعد التأكد من أن جميع القراءات تستخدم الـbatch/allocations.

### 4.5 المنافذ والمستودعات والسلال

#### إزالة توافق السجلات مجهولة الموقع

- حذف `SECURITY_LEGACY_SINGLE_OUTLET_BYPASS` من `config/security.php` وملفات البيئة والتوثيق والاختبارات.
- حذف وسائط وفروع `includeLegacy` من `OutletAccessService` والتقارير والتصدير.
- لا تستخدم الاستعلامات التشغيلية `orWhereNull('warehouse_id')` أو ما يعادلها لإظهار سجل قديم.
- `warehouses.outlet_id` يصبح إلزاميًا.
- `warehouse_id` يصبح إلزاميًا في السجلات التي لا يمكن تنفيذها فعليًا بلا مستودع: المعاملات، السلال، الورديات، mutations، أوامر الشراء والاستلام ومرتجعات المورد وopname.
- `transactions.cashier_shift_id` يصبح إلزاميًا بعد تحديث الـfactories والـfixtures وجميع مسارات checkout/sync.

#### عزل السلة

`warehouse_id` يُكتب حاليًا في كثير من إنشاءات السلة، لكن بعض قراءات Web/Mobile API لا تقيّد السلة به. المطلوب:

1. أن يكون `carts.warehouse_id` غير nullable.
2. أن تطابق عمليات active/held/hold/resume/update/delete/clear/checkout و`onlyCartIds` المستخدم والمستودع/الوردية النشطة.
3. أن يطبق Mobile API حراسة الوردية والعزل نفسيهما اللذين يفرضهما middleware `active_shift` في Web.
4. رفض استئناف سلة محفوظة في مستودع مختلف بدل نقلها بصمت.
5. تحديث fixtures التي تنشئ سلالًا أو معاملات مباشرة بلا وردية؛ لا يُضاف bypass للاختبارات.

#### ما لا يُحذف

- اختيار مستودع البيع الافتراضي عند فتح وردية دون تمرير `warehouse_id`؛ النتيجة ما زالت وردية لها مستودع صريح.
- `outlet_id = NULL` في الإعدادات والدفع والحسابات البنكية والتسعير وقوائم الأسعار والولاء والعروض وdine-in عندما يعني fallback عامًا موثقًا.
- حملات CRM العامة إن كانت مقصودة؛ لا تعامل كسجلات قديمة لمجرد NULL.
- إسناد المستخدمين إلى المنافذ وصلاحيات RBAC وقفل تبديل المنفذ أثناء وردية مفتوحة.

### 4.6 الدفع: tenders هي التفاصيل canonical والمعاملة هي الملخص

الحقول `transactions.payment_method/payment_status/cash/change` مستخدمة في واجهات وتقارير حالية، وليست كلها قديمة. كذلك يحتاج split tender إلى tenders متعددة. الخطة لا تستبدل عقد الإدخال الحالي بعقد جديد للعملاء.

#### الشكل الداخلي النهائي

- الدفع المفرد غير الآجل ينشئ tender واحدًا **عند تنفيذ الدفع/التحصيل**، لا بمجرد إنشاء معاملة غير مدفوعة.
- الدفع المقسّم ينشئ tenders متعددة كما هو حاليًا.
- `pay_later` لا ينشئ tender مدفوعًا وهميًا؛ ينشئ/يحدث receivable وفق المسار الحالي.
- المعاملة التي ما زالت `unpaid`، ومنها dine-in قبل التحصيل، لا تحصل على tender مدفوع؛ يُنشأ عند مسار الدفع الفعلي.
- المدفوعات الآجلة عند التحصيل تُسجل بالطريقة المالية الحالية، دون ازدواج tender أو receivable payment.
- `payment_method` في المعاملة يبقى ملخصًا: الطريقة نفسها للدفع المفرد، و`split` للدفع المقسّم.
- `payment_status` و`cash/change` يبقيان متاحين بالشكل الحالي، وتُثبت الاختبارات تطابقهما مع tenders.

#### المسارات التي يجب تحويلها قبل حذف أي عمود مكرر

- Web POS وMobile POS وoffline sync.
- `CheckoutService` و`TransactionTenderService` و`DineOrderService`.
- `PublicPortalController`؛ يجب أن ينشئ tender للدفع الإلكتروني كما يفعل POS.
- `PaymentWebhookController` لـMidtrans وXendit.
- إنشاء QRIS وتحديث `qr_string` ومرجع البوابة ورابط الدفع.
- تأكيد التحويل البنكي في `TransactionController`.
- `ExpirePendingTransactionsCommand` واستعادة المخزون عند الانتهاء/الفشل.
- `TransactionResource` والاستجابات العامة وAPI.
- الطباعة الحرارية والفواتير والتصدير وتقارير الوردية.

بعد ذلك يمكن حذف النسخ المكررة مثل `bank_account_id` وحقول gateway/reference/URL/QR من جدول المعاملة، **فقط إذا** وفر الـresource/الـview القيمة نفسها من الـtender المناسب. إذا كان أحد الحقول ملخصًا لا يمكن اشتقاقه بلا غموض، يبقى بوصفه ملخصًا موثقًا ولا يُحذف لمجرد التشابه.

لا تتغير حقول الطلب الحالية للدفع المفرد (`payment_method`, `cash`, `bank_account_id` ونحوها) لمجرد أن التخزين الداخلي أصبح tender. يضيف الاختبار تكافؤ single وsplit وpay-later وpending وpaid وfailed وexpired والتحصيل الجزئي/الكامل.

### 4.7 المالية والمرتجعات: تشديد الملكية دون افتراض أن كل NULL قديم

#### Payables

- يوجد payable يدوي بلا أمر شراء؛ لذلك لا يجوز اشتراط `purchase_order_id` أو اشتقاق موقعه من PO دائمًا.
- يضاف `outlet_id` صريح للـpayable.
- الـpayable المشتق من PO يأخذ المنفذ من مستودع الاستلام/PO.
- الـpayable اليدوي يتطلب منفذًا صريحًا من السياق المسموح للمستخدم.
- تُحدّث الاستعلامات والوصول و`PayableAgingService` على هذا العمود.

#### Receivables

- كل إنشاء إنتاجي حالي مرتبط بمعاملة، لذا يصبح `receivables.transaction_id` إلزاميًا بعد تحديث الـfactories والاختبارات.
- تكون سياسة حذف المعاملة `restrict` أو ما يعادلها؛ لا تُحذف معاملة وتترك سجلًا ماليًا بلا مصدر.
- يبقى `customer_id` nullable ما لم يتغير شرط البيع الآجل نفسه؛ هذا التغيير ليس جزءًا من التنظيف.
- حقل `receivables.access_token` غير المستخدم يُحذف، ولا يتأثر token مشاركة المعاملة الفعلي.

#### المرتجعات والحالات الوسيطة

- `sales_returns.cashier_shift_id` و`warehouse_id` قد يكونان NULL أثناء المسودة؛ هذه حالة حالية مشروعة وليست دليل legacy.
- عند الإكمال يجب أن تؤخذ الوردية والمستودع من المعاملة/السياق الفعلي، وأن تفشل العملية إذا تعذر تحديدهما.
- يفضل ملء المستودع من المعاملة عند إنشاء المسودة أيضًا، لكن لا يُفرض NOT NULL على كل الصفوف قبل تسوية سياسة المسودات.
- لا تُحوّل قيود الحالة إلى NOT NULL أعمى؛ يمكن استخدام تحقق التطبيق أو قيد مركب إن لزم.

### 4.8 Offline وService Worker

في `resources/js/Utils/offlineDb.js` توجد وظائف حالية ووظائف ترقية قديمة في الملف نفسه.

ما يُحذف:

- تطبيع صفوف queue الإصدار الأول وحقوله القديمة.
- قبول صفوف بلا warehouse/outlet scope أو اعتبار NULL مطابقًا لكل المواقع.
- منطق إنقاذ بيانات قديمة مجهولة المالك.

ما يبقى:

- مخطط queue الحالي وحالاته ومحاولاته ورسائل الخطأ.
- استرداد عناصر علقت في `syncing`.
- `client_uuid` و`sync_fingerprint` ومنع الإرسال المكرر.
- عزل المستخدم/المستودع/المنفذ والتحقق من الوردية عند المزامنة.
- آلية versioning وحذف caches القديمة في `public/sw.js`؛ هذه آلية نشر مستقلة ومطلوبة مستقبلًا أيضًا.

لأن فقدان بيانات العميل المحلي مقبول في هذا الانتقال، تُنفذ خطوة destructive browser reset موثقة: إغلاق صفحات التطبيق الأخرى، حذف IndexedDB القديم وإعادة إنشائه بالمخطط الحالي، وتحديث الـservice worker ومسح caches القديمة. لا تُترك قاعدة قديمة تتدرج عبر upgrade handler لم يعد آمنًا.

### 4.9 الأوامر والفحوص المخصصة للترقية

| الأمر/المكوّن | القرار |
|---|---|
| `AuditLegacyOutletCommand` و`outlet:legacy-audit --backfill` | يحذف الأمر والتسجيل والاختبارات الخاصة بإصلاح البيانات القديمة |
| `InventoryReconcileCommand` و`inventory:reconcile` | يحذف بعد اختفاء `products.stock`؛ لا يبقى هناك رصيدان يحتاجان reconcile |
| `InventoryAuditMultiunitCommand` (`inventory:audit-multiuint`) | تحذف فحوص الانحراف المرتبطة بخطأ قديم مثل `salesReturns()` و`expirationCandidates()` |
| فحص `batchDivergence()` | يُستخرج/يُعاد تسميته ليصبح تدقيق invariant حالي إذا أثبتت الاختبارات فائدته |
| `AuditOutletCommand` | يعاد كتابته ليفحص الملكية والمخزون canonical فقط، ويبقى `--strict` بوابة فشل للـinvariants |
| schema guards في demo/runtime | تحذف إذا كان غرضها دعم جداول ناقصة قديمة؛ تبقى فحوص البيئة والحماية |

تُحدّث أو تُستبدل `AuditOutletCommandTest` و`InventoryReconcileCommandTest` و`StockInvariantTest` وفق القرار أعلاه؛ لا تُحذف التغطية دون بدل يختبر الحالة الجديدة.

### 4.10 الحقول والإعدادات المرشحة للحذف بعد إثبات عدم وجود مستهلك

الجرد الحالي يثبت أن العناصر التالية إما مؤشرات قديمة أو مخازن مكررة/غير مستخدمة، وتُحذف في مرحلتها المناسبة:

- `products.stock`.
- `transaction_details.product_batch_id`.
- `stock_mutations.batch_number` و`stock_mutations.expired_at`.
- `customers.postal_code`.
- `product_units.sku_suffix`.
- `receivables.access_token`.
- `cashier_shifts.cash_in_total` و`cash_out_total` من قاعدة البيانات.
- `dine_orders.payment_method` و`payment_reference` و`payment_url`، مع بقاء `payment_option` و`payment_status` المستخدمين.
- مفتاح `dine_in_pay_online_enabled` من seeder وتوثيق الإعدادات؛ لا يوجد قارئ تطبيقي له في المرجع.
- `SECURITY_LEGACY_SINGLE_OUTLET_BYPASS` ومسارات `includeLegacy`.

**استثناء مهم:** مفاتيح `cash_in_total/cash_out_total` في استجابة الوردية تبقى إذا كانت جزءًا من العقد، لكن تُحسب من `shift_cash_movements` بدل تخزين نسخة ثانية.

أما الحقول أو الإعدادات الأخرى التي لا توجد لها قراءة حالية، مثل بعض خيارات dine-in أو timeout، فلا تُحذف تلقائيًا ضمن مهمة إزالة التوافق ما لم يُثبت أنها أضيفت لذلك الغرض. «غير مستخدم» و«قديم للتوافق» تصنيفان مختلفان.

## 5. قائمة «لا تحذف»

هذه العناصر قد تبدو كنُسخ احتياطية أو fallbacks، لكنها مطلوبة للوظائف الحالية:

- encrypted casts لأسرار `PaymentSetting`.
- الإعدادات العامة وfallback `outlet_id = NULL` في الدفع والحسابات البنكية والتسعير وdine-in.
- مستودع PUSAT المركزي و`setup_warehouse_id` ومسار الإعداد الأولي.
- فتح وردية باختيار مستودع البيع الافتراضي عند عدم تمرير المستودع صراحة.
- nullable للمسودات والحالات غير المكتملة حيث يكون ذلك جزءًا من دورة الحياة.
- ملخصات المعاملة والوردية وحقول API الحالية، ولو أصبحت مشتقة.
- FEFO وbatch allocations واستعادة الكميات عند الإلغاء/المرتجع.
- صلاحيات Spatie وعزل المنافذ وقيود step-up والموافقات.
- `client_uuid` و`sync_fingerprint` وoffline retry/recovery.
- cache versioning في service worker.
- حماية demo data في production وحماية جداول المناطق أثناء demo reset.
- جداول المناطق `indonesia_provinces/cities/districts/villages` وعلاقات العملاء بها.
- seeders الحتمية وقابلية تكرارها بأمان؛ هذه ليست backfills لبيانات قديمة.

## 6. ترتيب التنفيذ الآمن

كل مرحلة يجب أن تنتهي باختبارات ناجحة قبل الانتقال إلى التالية. لا تبدأ بحذف الأعمدة.

### المرحلة 0 — تثبيت العقود الحالية

1. إضافة characterization tests لاستجابات المنتجات والمعاملات والوردية والتصدير والطباعة.
2. تغطية single/split/pay-later/gateway وpublic portal وoffline.
3. تغطية المخزون متعدد المستودعات والوحدات والـbatches والمنتجات المركبة.
4. تسجيل السلوك الحالي المقصود للحالات العامة والمسودات حتى لا تدخل تغييرات محاسبية غير مقصودة.

### المرحلة 1 — مصدر canonical للمخزون والوحدات والـbatches

1. توحيد الكتابة عبر خدمة المخزون.
2. تحويل كل القراءات إلى الـpivot مع إبقاء شكل الاستجابة.
3. فرض الوحدات الصريحة وإزالة افتراض ID `1` وfactor `1` للمنتج العادي.
4. إكمال allocations في كل المسارات.
5. حذف dual writes ثم الأعمدة القديمة في commit لاحق واضح.

### المرحلة 2 — ملكية المنافذ والمستودعات والسلال

1. جعل كل مسارات الإنشاء تكتب ownership كاملًا.
2. توحيد Web وMobile API وoffline على الوردية والمستودع النشطين.
3. حذف bypass و`includeLegacy` وفروع NULL التشغيلية.
4. تشديد القيود بعد نجاح اختبارات الإنشاء والوصول والتقارير.

### المرحلة 3 — توحيد الدفع والمالية

1. إنشاء tender واحد للدفع المفرد والحفاظ على split tenders.
2. تحويل public portal وwebhooks وQRIS والتأكيد البنكي والانتهاء والطباعة والقراءات.
3. اشتقاق حقول العرض المكررة وإثبات تطابق العقود.
4. إضافة ownership للـpayables وتشديد receivables.
5. حذف الأعمدة المكررة التي ثبت عدم الحاجة إليها فقط.

### المرحلة 4 — إزالة أدوات الترقية وoffline v1

1. حذف أو إعادة كتابة الأوامر وفق الجدول السابق.
2. حذف backfills وschema guards ودور normalization للبيانات القديمة.
3. تنفيذ destructive browser reset مع الاحتفاظ بوظائف offline الحالية.
4. حذف الإعدادات والحقول الميتة المؤكدة فقط.

### المرحلة 5 — baseline نهائي وreset

1. دمج الـmigrations في مخطط الإنشاء النهائي ونقل defaults إلى seeders.
2. اختبار قاعدة فارغة على SQLite وMySQL.
3. تنفيذ runbook الحذف على بيئة disposable أولًا.
4. بعد قبول النتيجة فقط، تنفيذها على البيئة المقصودة.

## 7. Runbook الحذف وإعادة الإنشاء

> هذه الخطوات للتنفيذ اللاحق، ولم تُنفّذ مع إنشاء هذا المستند.

### قبل الحذف

1. تفعيل maintenance mode وإيقاف workers وجدولة المهام ومنع checkout/sync أثناء الانتقال.
2. أخذ نسخة احتياطية رغم أن البيانات تجريبية؛ الهدف هو إمكانية التراجع عن خطأ تشغيلي، لا دعم ترقية البيانات.
3. الحفاظ على `.env` و`APP_KEY` والإعدادات السرية خارج قاعدة البيانات وفق سياسة النشر، وعدم توليد مفتاح جديد بلا حاجة.
4. التأكد من أن النسخة المنشورة تحتوي جميع المراحل السابقة؛ لا تُنشأ قاعدة جديدة ثم يشغّل عليها كود ما زال يعتمد على الأعمدة المحذوفة.
5. تجهيز مصدر بيانات المناطق المرجعية قبل الحذف:
   - migrations الحالية تنشئ جداول `laravolt/indonesia` لكنها لا تملؤها.
   - `DatabaseSeeder` وتوثيق البدء في المرجع لا يثبتان أن `migrate:fresh --seed` يعبئها.
   - لذلك يجب تثبيت أمر الـseeder المدعوم من نسخة الحزمة المثبتة، أو تجهيز dump **للبيانات المرجعية فقط** لهذه الجداول.
   - تُسجل أعداد المحافظات والمدن والمناطق والقرى قبل الحذف للمقارنة بعد الاستعادة.
6. إخطار المستخدمين بإغلاق كل tabs، وتنفيذ حذف IndexedDB وcache reset المخطط له.

### على قاعدة MySQL disposable أولًا

```bash
php artisan migrate:fresh --seed --force
```

ثم:

1. استعادة/زرع بيانات المناطق بالطريقة التي ثبتت في خطوة التحضير.
2. تشغيل setup وإنشاء منفذ بائع ومستودعه ومستخدميه ووحدات المنتجات وإعدادات الدفع اللازمة.
3. التأكد من أن جداول المناطق غير فارغة وأن اختيار منطقة العميل يعمل.
4. تشغيل اختبارات القبول والسيناريوهات اليدوية أدناه.
5. التأكد من أن إعادة تشغيل seeders المقصودة وحدها لا تضاعف الأدوار والإعدادات والوحدات؛ لا تُعد `migrate:fresh` على قاعدة تحتوي عملًا جديدًا.

### على البيئة المقصودة بعد القبول

1. تكرار النسخة الاحتياطية والتحقق من maintenance mode وإيقاف الكتابات.
2. تنفيذ `migrate:fresh --seed --force` مرة واحدة بشكل مقصود.
3. استعادة بيانات المناطق والتحقق من أعدادها.
4. إكمال setup بالبيانات الحقيقية الجديدة، لا باستيراد السجلات التشغيلية التجريبية القديمة.
5. مسح caches الخاصة بالتطبيق وإعادة تشغيل workers وفق آلية النشر.
6. نشر frontend الجديد وservice worker، ثم التحقق من أن العميل أعاد إنشاء قاعدة offline النظيفة.
7. تنفيذ smoke test للبيع والدفع والتقرير والمزامنة قبل رفع maintenance mode.

## 8. الاختبارات ومعايير القبول

### اختبارات آلية مطلوبة

- اختبار fresh migrations وseeders على قاعدة فارغة.
- اختبار يثبت عدم وجود الأعمدة والأوامر والإعدادات المحذوفة.
- اختبارات canonical stock: البيع، الإلغاء، المرتجع، الاستلام، مرتجع المورد، opname، التحويل، المنتج المركب.
- اختبارات تمنع الكسور غير الصحيحة في الوحدات وتثبت base-unit `before/after`.
- اختبارات FEFO والبيع من أكثر من batch واستعادة allocations.
- اختبارات تمنع سلة أو معاملة أو mutation تشغيلية بلا مستودع، وتمنع الوصول المتقاطع بين المنافذ.
- اختبارات عقود Product/Transaction/CashierShift resources والتصدير والطباعة.
- اختبارات single/split/pay-later وgateway/webhook/public portal/QRIS/expiry.
- اختبارات payable اليدوي والمشتق من PO وreceivable المرتبط بالمعاملة.
- اختبارات offline للـidempotency وretry وrecovery والعزل بعد حذف ترقية v1.
- اختبار يحافظ على الإعدادات العامة وfallbacks المقصودة وعدم تسريبها إلى منفذ غير مصرح.

الأوامر الأساسية في بيئة تحتوي PHP وdependencies:

```bash
php artisan test
npm run build
```

`phpunit.xml` يستخدم SQLite in-memory. يجب بالإضافة إليه تشغيل fresh migrate والـsmoke tests على MySQL لأن قيود المفاتيح والفهارس وسلوك قاعدة الإنتاج لا تثبتها SQLite وحدها. لا يوجد حاليًا script مستقل لاختبارات frontend في `package.json`؛ لذلك يلزم فحص متصفح يدوي أو إضافة اختبار متصفح في مهمة منفصلة، ولا يُعد `npm run build` بديلًا عنه.

### سيناريوهات قبول يدوية

1. إنشاء منتج واستيراده وتعديله وعرض رصيده في منفذين.
2. فتح وردية والبيع نقدًا وبالتقسيم وآجلًا وإلكترونيًا، ثم إغلاق الوردية ومطابقة التقرير.
3. hold/resume ومسح السلة على Web وMobile API مع محاولة وصول لمستودع آخر.
4. مرتجع بيع كامل وجزئي واستلام مشتريات وopname وتحويل مخزون.
5. بيع بوحدات متعددة ومن batches متعددة والتحقق من الطباعة والتصدير.
6. دفع من بوابة العميل واستقبال webhook وانتهاء معاملة pending واستعادة الرصيد.
7. dine-in والمرتجعات والتقارير والأرباح وCRM والإعدادات العامة.
8. قطع الشبكة وإنشاء معاملة وإعادة الإرسال مرتين والتأكد من عدم التكرار.
9. اختيار محافظة/مدينة/منطقة/قرية للعميل بعد reset.

### شرط الإنجاز النهائي

لا يكفي نجاح الاختبارات وحده. يجب أيضًا أن يثبت بحث الشيفرة عدم بقاء مراجع تشغيلية إلى:

- `products.stock` كمصدر تخزين.
- `product_batch_id` في تفاصيل المعاملة.
- `SECURITY_LEGACY_SINGLE_OUTLET_BYPASS` أو `includeLegacy`.
- `inventory:reconcile` و`outlet:legacy-audit`.
- backfills وschema guards الخاصة بالتثبيتات القديمة.
- تطبيع offline v1 وNULL operational scope.

وأن تبقى الوظائف والعقود المتفق على بقائها في قائمة «لا تحذف».

## 9. قرار الإصدار والنشر

هذه النسخة يجب أن تُعلن كنقطة قطع مع الترقية الداخلية القديمة: لا تدعم تشغيل الكود الجديد على قاعدة قديمة ثم انتظار backfill، ولا تدعم استيراد بيانات تثبيت قديم تلقائيًا. المسار الوحيد المدعوم هو قاعدة فارغة + seeders + بيانات المناطق + إعداد جديد.

بهذا يختفي عبء التوافق فعليًا، بدل نقله من migrations إلى خدمات وشروط مخفية، مع بقاء سلوك النظام الحالي ظاهرًا للمستخدم كما هو.
